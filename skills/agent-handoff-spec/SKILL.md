# 交给另一个 Agent 执行的交接件

## When to Use
- 用户把一件事拆给两个执行方：「你只需要把 X 总结出来，交由 <@另一个 Agent/人> 去做 Y」「建好后交还给你，你按经验审查」。
- 用户要一份**别人能照着做**的文档 / 规范 / 经验总结，而不是你自己把产物做出来。
- 你已经开工，用户中途改口径（「你只需要…」）⇒ 立刻停手，转成出交接件。
- 用户说「我看不到你说的 §X.Y」⇒ 走 Step 3 的交付格式。

不适用：你把活直接干完（普通任务）、或只给用户一个短回答。

## 第 0 条：先判定自己的交付物是「规格」还是「产物」

**用户点名了另一个执行方 ⇒ 你的交付物是规格，不是产物。** 从「交由 X 构建」这句起，写 skill / 写脚本 / 建文件的行为就要停：继续建产物等于替对方干活，两边的改动会打架，而且抢了对方的活。

你只做三件：出规格 → 交付给用户 → 按验收清单审对方交回的东西。

## Step 1 — 交接件的骨架

一份交接件 = 任务书 + 经验 + 验收清单，缺一块对方就会自己发挥。骨架（可直接从 `templates/handoff-spec.md` 复制）：

| 节 | 内容 | 为什么不能省 |
|---|---|---|
| 0 分工 | 谁做什么 + 硬约束（保密、不许外发、数字必须实测） | 对方要据此判断哪些不该碰 |
| 1 任务书 | 要建/改的**确切路径、确切名字**，以及「完成意味着什么」 | 名字不一致 = 返工 |
| 2 通用化边界 | 什么是规则、什么是实例；哪些既有词表不许发明新条目 | 否则写成第二份「某个具体项目的文档」 |
| 3 经验正文 | 见 Step 2 的证据规则 | 这是对方最缺的东西 |
| 4 过时信息清单 | 表：位置 / 现在写的 / 实测事实 / 证据（命令或 commit）；**分「本次要改」与「只登记」** | 不分范围，对方会越界改到别人的地盘 |
| 5 素材出处 | 对方能自己打开的路径（配置、脚本目录、历史记录）+ 一句「别抄我这份，先自己核」 | 防它以讹传讹 |
| 6 验收清单 | **编号、逐条可判定**；同时是对方的自查表和你的审查表 | 两边用同一份，别各写一套 |
| 7 待用户拍板项 | 每个决策：实测事实表 + 2–3 个选项（各带代价）+ 你的建议 + 「你只需回答什么」 | 让用户回一句就能放行 |
| 8 交接方式 | 谁是第一方、第二方、何时交还、卡住找谁 | 闭环 |

**改名类要求要列全**：目录名、frontmatter `name:`、description、以及所有引用它的地方（README 索引、安装命令里的 skill 列表）——只写「改名」两个字，对方就只改目录名。

**涉及远端/标识符时**，交付前实测一遍再写进任务书：本地目录名与远端仓库名经常不一致（本地已改名、远端没改 → 旧地址 404）。核法：`gh repo list <owner>`、`curl -o /dev/null -w '%{http_code}' <url>`。别照抄本地目录名写安装命令。

## Step 2 — 证据规则（决定这份交接件有没有用）

- **每条经验挂实测证据**：数字、报错原文、文件路径。凡标「实测」的后面必须有东西；**推演不写，宁缺勿造**。
- **没测过的标「待核」**，并写清「要到哪一层才算核过」。把待核项当已确认，是这份文档最贵的错误。
- **报错原文照抄**（如 `duplicate unique key given: [WFL-08-01,A,2]`），不要换成「会报错」——原文是对方日后唯一能复现、也是这份经验最值钱的部分。
- **硬约束里写死：不许为「更通用」删掉具体证据。** 「通用」= 规则通用，不是把数字抹掉。
- **给规则起名**（「阶段要分开说」「先钉死边界」），审查时才能指名道姓地核。
- **实例与常量分开**：某库的实测数字（42 管 / 162 槽 / 35 条断言）只能作证据并标明属于哪个实例，不得写成通用常量。

## Step 3 — 交付给用户（格式）

- **待办 / 决策要自成一个文档**，不要只作为大文档里的 §8.1 / §8.2 / §8.3。
- **不要在聊天里用编号指代文件里的小节**（「见 §8.1」）—— 用户看不到那个文件就完全接不上。要么把内容**整段贴进消息**，要么另出一份自包含的文档**并同时贴正文**。
- 附件用 `MEDIA:/绝对路径` 发出去；正文照贴，让用户不打开文件也能回。
- 决策项排成「回一句就能放行」的形状（`A1 = ①；A2 = A；A3 = ①`）。
- **过程文档与交付物分开放，而且要落定版本。** 交接件、审查意见、决定记录都是过程文档；交付物是产物本身。放进被交付的仓库时统一收进 `docs/`，并在 README 写一句「`docs/` 是过程记录，交付物只有 `skills/`（或对应目录）」；不要与交付物平级散在根目录，也不要长期挂在「未跟踪」——用户会问「这几个文件要不要入库」，答完就该有个确定归宿。

## Step 4 — 审查交回的东西

- **按任务书第 6 条的验收清单逐条核**，出审查意见（哪几条通过、哪几条不通过、依据是什么）。不要只说「整体不错」。
- **对方的总结是自述，不是事实。** 数字自己复现：连库、跑脚本、读文件，抽查 §2 里最关键的假设 + 任一标「实测」的结论。对方说「已成文」「已上传」「已通过」都要自己读回一次。
- **你交出去的素材也可能是错的，而且对方可能改对了。** 对方提出「素材 vs 实测」不符时，**逐条去测**：成立就认，并在审查意见里单列一节（写明「这条错在我、实测值是 X」）。对方没照抄你的数字、而是复现后回头改你，是这份交接件最值钱的产出，不是要辩护的地方。
- 引用性检查：`name:` 与目录名一致、description 开头自含触发、`references/` 里的相对链接指向存在的文件、README 的安装命令与远端实际名字一致。
- **审查意见的固定形状**：结论一句话（通过 / 有条件通过 / 不通过）+ 逐条判定表（条目 / 结果 / 你核的方式）+ 独立复现的数字表（写清命令）+ 分级建议（**不阻塞的 P3** 与**阻塞项**分开，别把一行小改写成「不通过」）+ 下一步按依赖序。落成文件，别只在聊天里说。
- **环境级故障不算在对方账上。** 审查中撞上的故障，先证明是环境还是产物（例：把对方的库**复制**到 scratch 独立跑一遍，再在副本上另起一个进程跑一遍 —— 两条都通过就说明产物是好的）。结论里单列一节，给出修法，**但共享资源（长跑的 server、别人正在用的进程）不要擅自重启/杀掉**，把命令交给用户。
- 只审不改：对方名下的产物由对方改，你把它的问题列清楚。
- **写 / 改类验证一律在副本上做，做完回头证明源侧没被碰过。** 要验「加一支记录 / 改一行 / 触发某个约束」这类结论，先 `cp -R` 库或产物目录到 scratch，在副本上写；测完立刻把**源侧**的计数与体检读回来（行数、`dolt_test_run()` 之类）并写进报告，附一句「活库零影响」。理由：审查不能改动被审对象 —— 一旦在线上写了，你既污染了它，也再分不清后面的差异是你造成的还是本来就有。
- **「装上了」也要自己读回一次。** 交付物安装后，用 `skill_view(<name>)` 看 `readiness_status` 与 `linked_files` 是否齐全（references / scripts 一个不缺），再看该 profile 的安装记录（`install_path` / 文件数 / `scan_verdict` / pin 住的 commit）。安装落在哪个 profile 由会话的 `HERMES_HOME` 决定：在 A profile 的会话里跑 `hermes skills install`，装进的就是 A。别把「命令没报错」当成装好了。

## 陷阱

- **用户点名执行方 = 收手信号。** 最常见的越界是继续做产物。
- **「过时信息」要分范围。** 本体仓库里的要改；别处（别的 vault、别的 profile 的笔记、外部脚本目录）只登记。擅自扩大工作面会把一次任务变成三次。
- **任何一次迁出/改名/删除之后，顺手 grep 全部引用旧名的地方**（README 目录表、生成器里的默认路径、「唯一真相源」式断言），一次改完，改不到的登记。删除做完了文档没跟，就是下一次会话踩的坑。
- **别相信文件名**：README 的目录表是意图不是事实 —— 定位一律靠实测列目录（`search_files (target='files')`，不是照着文档抄）。
- **用户回「A1 的①、A2 的 A」这类口令后**，落地动作（改名、修文档、互留指针）是你的活，别又派回给第二个执行方——那是它范围外的改动。
- **提问与回答之间，共享状态会变。** 用户问「这几个文件要不要入库」时，**先 `git status` / `git log origin/main..HEAD` 再答**：对方可能在提问之后已经做完、提交、推送了，照着提问时看到的状态回答就是答非所问（还会把自己的旧观察当成事实复述）。审查前同样要重新取一次 HEAD，别审一个已经被推过的旧 commit。
- **对方可能和你的进程并行跑在同一个工作目录里**。开工前先看 `git log`/文件 mtime 判断「这一步是不是已经被做掉了」，做掉的直接核验、不重复做；重复做的代价是两份产物打架，各自看起来都对。
